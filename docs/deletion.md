# Удаление аккаунта

DeleteAccount реализует api.md 2.5 / grpc-api.md 7.1 в FIN-219. Создание, подтверждение
и Watch — [verification.md](verification.md). Используются go-tombstone v0.1.0,
go-outbox v0.1.0, владелец ответа go-idempotency с Resource (FIN-230) (FIN-226) и связь ключей
Start с заявкой через Resource библиотеки (FIN-230). Миграция 000002 хранит данные
своей попытки непосредственно в phone_verification.

## Доступ и результат

Метод доступен bank-bff с проверенным пользовательским access JWT. ID берётся только
из sub, не из тела запроса. Точное правило ModelUser разрешает проход с tombstone,
чтобы повтор удаления возвращал OK. Подпись, срок JWT, сервисный токен и ACL всё равно
проверяются; остальные вызовы удалённого пользователя получают TOKEN_REVOKED.

Ответ OK означает синхронное удаление локальных данных и надёжное сохранение задачи
удаления у соседей. Доставку не ждём в пользовательском RPC. Повтор с тем же старым
ID возвращает OK без нового события. При повторной регистрации телефона выдаётся
новый UUID; повтор старого DeleteAccount не удаляет новый аккаунт.

## Одна транзакция на primary

1. go-tombstone.Purge берёт Guard пользователя. Готовый tombstone завершает повтор.
2. Адаптер блокирует принадлежащие пользователю ключи идемпотентности:
   `scope=$1::uuid OR owner_id=$1::uuid`, `FOR UPDATE NOWAIT`.
3. Телефон читается из app_user FOR UPDATE. Заявки телефона блокируются FOR UPDATE до поиска ключей, затем по Resource блокируются
   через NOWAIT и удаляются ключи Start этого телефона: успешные ответы, ещё не
   завершённые резервы и сохранённые busy-отказы, в том числе созданные до аккаунта
   без OwnerID. Ограничение scope/endpoint не затрагивает чужие no-user ответы.
   Удаляются адресные ключи и app_user;
   каскады удаляют согласия, сессии, все refresh и связанные заявки.
4. По телефону удаляются все оставшиеся phone_verification, включая неподтверждённые
   и результаты без user_id. Зашифрованные ответы/registration_token не сохраняются.
5. Удаляются ещё не доставленные user.timezone_changed этого ID. Публикуется
   user.deleted с protobuf PurgeUserDataRequest{user_id}; телефона и токенов в нём нет.
6. Библиотека сохраняет tombstone; общий commit фиксирует все эффекты.

Ошибка записи или отмена до commit откатывает всё. Если локального app_user уже нет,
но tombstone отсутствует, проверенный ID всё равно получает tombstone и задачу очистки
соседей: частично восстановленная БД не должна оставить чужие данные без запроса.
Документы согласий общие и не удаляются. Окна rate_limit_window сохраняются до штатной
очистки, включая телефонные лимиты (решение владельца 19.10.2026).

Start не удерживает транзакцию во время внешнего обращения. Если DeleteAccount
удалил его ключ/заявку, финальный DoReserved/CAS не может создать их заново и выдать
секрет; опоздавшее подтверждение не находит заявку. Явный отказ провайдера удаляет
только свои start_* поля, сохраняя библиотечные связи busy-ответов для последующего адресного удаления.

Auth replay сначала блокирует ключ, затем Guard владельца. Поэтому удаление под Guard
не ждёт занятого ключа: PostgreSQL 55P03 превращается в ErrReplayBusy, вся транзакция
откатывается, через 20 мс начинается новая. Это освобождает Guard для завершающегося
replay. Другие SQL-ошибки не повторяются. Общая граница — дедлайн вызывающего и максимум
10 секунд; внутренний дефолт сервера может быть короче. Повтор с истёкшим JWT требует
нового входа, старые refresh уже отозваны.

## Доставка и настройки

OUTBOX_DELETION_TARGETS по умолчанию bank-statement-data,analytics,assistant. Все три
обязательны; дополнительные получатели допустимы. OUTBOX_TIMEZONE_TARGETS остаётся
bank-statement-data,assistant. Каждому уникальному соседу нужен PEER_<NAME>_ADDR,
**включая новый обязательный PEER_ANALYTICS_ADDR**. Неверная конфигурация останавливает
сборку; сетевой отказ настроенного соседа запуск и локальное удаление не блокирует.
Пул OUTBOX_DB_MAX_CONNS должен вмещать число уникальных соседей обеих тем + 3:
минимум 6 при стандартных маршрутах, значение по умолчанию 8.

go-outbox доставляет каждый PurgeUserData независимо с сохранением незавершённых
получателей в PostgreSQL. Уже подтвердивший получатель не ждёт медленного соседа.
После перезапуска остаются только не подтверждённые задания. Доставка at-least-once:
повтор безопасен по контракту получателя; порядок тем и событий не гарантируется.
Получатели обязаны атомарно ставить свой tombstone с удалением и останавливать им
отложенные записи, включая старый SetUserTimezone. Их реализация этим PR не заявляется.

Исходящий RPC несёт только сервисный токен user и получает дедлайн 30 секунд,
штатные ограниченные повторы UNAVAILABLE внутри надёжных повторов outbox. Входные
authorization, IP, версия клиента и ключ идемпотентности дальше не передаются.

## Метрики и проверки

finassist_outbox_rows{target}, finassist_outbox_oldest_age_seconds{target} и
finassist_outbox_delivery_errors_total{target} объединяют обе темы по получателю.
Метки — ограниченные target, пустой target до fanout и unconfigured; user_id, payload
и секретов среди меток нет. Требуется внешнее правило
`finassist_outbox_oldest_age_seconds > 3600` для всех target, включая пустой и
unconfigured (пример выдержки 1 минута). Оно обнаруживает и задержку PurgeUserData.
Конфигурация уведомлений в infra — отдельная работа, наличие метрик не включает алерт.

Юнит-тесты проверяют транзакционные границы, ошибки, повторы, идентичность, допуск
повторного удаления и protobuf события. PostgreSQL-тесты проверяют NOWAIT, откат Guard
и адресную очистку. API-тесты проходят полную сборку: каскады и заявки без user_id,
удаление cached-секретов, повтор, изоляцию пользователей, новый UUID, откат SQL-ошибки
и конкурирующие auth/profile операции. Уже выполняющийся SetUserTimezone проверяется
отдельно: удаление завершается в пределах дедлайна, пока старый RPC заблокирован.
Два свободных соседа получают PurgeUserData сразу; после освобождения третьего
доходит и его задание, поздний ack старого события не восстанавливает очередь. Три настоящих gRPC-получателя проверяют
недоступность, медленный ответ, метрики возраста и восстановление после пересоздания
App с новыми пулами и соединениями. Продовый стенд этим не проверяется.
