# Схема БД `user`

Задача — [FIN-112](https://finassist.youtrack.cloud/issue/FIN-112). Миграция — [`migrations/000001_init_schema.up.sql`](../migrations/000001_init_schema.up.sql), проверки инвариантов — [`migrations/schema_test.go`](../migrations/schema_test.go). Смысл полей — `fin-assist/contracts`: `docs/api.md` 1–2, `docs/grpc-api.md` 6, 6.1, 7.1; решения — Confluence PF «Архитектура» («Аутентификация», «Идемпотентность», «Идентификаторы», «PostgreSQL», «Бэкапы»).

## Общие правила

- **Секреты не хранятся в открытом виде.** `verification_token`, `registration_token`, refresh — 256 случайных бит, в БД только SHA-256 (`bytea`, 32 байта, `CHECK`). Соль и медленный хеш не нужны: перебор 2²⁵⁶ невозможен, а поиск по хешу — точное совпадение по уникальному индексу. Сравнение «за постоянное время» (api.md 1.2) обеспечивает именно поиск по хешу: время зависит от хеша, а не от совпавшего префикса токена.
- **Результат для повторной доставки** (пара токенов существующего пользователя или `registration_token` нового — 15 минут с подтверждения, api.md 1.2) по хешу не восстановить, поэтому он хранится шифротекстом ключа сервиса (AES-GCM, `result_key_id` — какой ключ) и стирается при закрытии заявки или по истечении 15 минут. Ключ — в секретах, не в БД.
- **Ключи подписи JWT в БД нет** (ниже).
- **Время бизнес-правил пишет сервис** из внедрённых часов (`AGENTS.md`, Time): `expires_at`, `verified_at`, `rotated_at`, `revoked_at`, `granted_at`. `now()` по умолчанию — только у технических `created_at`.
- **ID** («Идентификаторы»): `app_user.id` выходит за пределы БД — `uuid` UUIDv7 (`uuidv7()` PostgreSQL 18). Остальные ID внутренние — `bigint GENERATED ALWAYS AS IDENTITY`; ширина по числу вставок за жизнь (заявки и ротации refresh — очереди, растут непрерывно).
- **Тексты-коды** (`theme`, тип согласия) — `text` с `CHECK`, а не `enum` PostgreSQL: новое значение — `ALTER TABLE … DROP/ADD CONSTRAINT … NOT VALID` + `VALIDATE` без перезаписи таблицы, тогда как значение `enum` удалить нельзя.
- **Таблицы библиотек** (outbox FIN-109, идемпотентность FIN-78, tombstone FIN-110) здесь не создаются: у библиотек свои источники миграций и таблицы версий (`docs/migrations.md`). Сейчас библиотеки — каркасы без миграций и тегов, поэтому в `MigrationSources()` они появятся вместе с их выпуском.

## Сущности

### `consent_document`, `consent_current` — документы согласий (1.6)

- `consent_document (type, version)` — PK; `title`, `url` (только `https://`). Новая версия — новая строка, старые остаются: на них ссылаются данные согласия.
- `consent_current (type)` — PK, ссылка на `(type, version)`: «текущая версия» — одна на тип по построению, отдельный флаг `is_current` с частичным уникальным индексом не нужен.
- Наполняются миграцией данных (новая версия документа — новый файл миграции): документы меняют юристы и релизом, а не пользователи. Альтернатива — конфигурация сервиса; минус — версии в БД нужны для внешних ключей `user_consent`.
- `type` — открытый код (`personal_data`, `assistant`; формат проверяется `CHECK`), а не закрытый список: новый тип согласия — новая строка (`consents[]` списком, FIN-82).

### `app_user` — пользователь и профиль (2.1–2.2)

| Столбец | Зачем |
|---|---|
| `id uuid` | UUIDv7, `user_id` во всех сервисах |
| `phone text` | E.164, `CHECK '^\+7[0-9]{10}$'` (api.md 1.1: только `+7` и 10 цифр); `UNIQUE` |
| `theme text` | `system` / `light` / `dark`, `CHECK` |
| `timezone text` | IANA, по умолчанию `Europe/Moscow` (1.3); корректность имени проверяет сервис по базе поясов Go — той же, по которой считают потребители, а не `pg_timezone_names` |
| `settings_version bigint` | версия настроек для `SetUserTimezone` (grpc-api.md 6.1): `UPDATE … SET timezone = $2, settings_version = settings_version + 1 … RETURNING settings_version` и строка outbox в той же транзакции |
| `created_at` | дата регистрации (2.1) |

**«Телефон уникален среди живых пользователей» — простой `UNIQUE (phone)`, потому что удалённого пользователя в таблице нет.** Удаление аккаунта удаляет строку `app_user`, внешние ключи с `ON DELETE CASCADE` удаляют согласия, заявки с его `user_id` (подтверждённые для существующего пользователя и закрытые `Register`) и сессии (refresh); остальные заявки на его номер `user_id` не имеют и остаются до очистки (вопрос 6). Что `user_id` удалён, помнит tombstone библиотеки (FIN-110) — в нём только `user_id` и момент удаления, без ПДн («Аутентификация»).

Альтернатива — мягкое удаление (`deleted_at`) с частичным `UNIQUE (phone) WHERE deleted_at IS NULL`. Отклонил: строка с телефоном удалённого пользователя — это ПДн, которые нужно стирать отдельно (152-ФЗ, «удаляет все данные»), а любой новый запрос обязан помнить `WHERE deleted_at IS NULL`. Плюс удаления строки — опоздавшая запись (транзакция, прочитавшая пользователя до удаления) падает на внешнем ключе, а не воскрешает данные: это и есть защита FIN-110, п. 5, для таблиц `user`.

### `user_consent` — согласия пользователя (`consents[]`, 1.3, 2.3, 2.4)

- Строка на одну выдачу согласия: `type`, `version` (внешний ключ на документ), `granted_at`, `revoked_at`. История остаётся: отзыв ставит `revoked_at`, повторная выдача — новая строка.
- **Одно действующее согласие на тип**: `UNIQUE (user_id, type) WHERE revoked_at IS NULL`. Тот же индекс с `INCLUDE (version)` отвечает `GetAssistantConsentStatus` index-only сканом без чтения истории.
- Согласие на ПДн из 1.3 — строка `personal_data` при регистрации, в одной транзакции с `app_user`. В `consents[]` профиля оно не входит (api.md 2.1) — это фильтр чтения, а не схемы.
- PK `(user_id, id)` — `user_id` первым, как в остальных сервисах (Confluence «Хранение данных»: `user_id` в каждом первичном ключе).
- «Устаревшая версия → `CONSENT_OUTDATED`» — проверка сервиса (`version = consent_current.version`), а не схемы: в истории законно лежат старые версии.

### `phone_verification` — заявки на верификацию (1.1–1.3)

Состояния — производные от столбцов, без отдельного `status`:

| Состояние | Условие |
|---|---|
| `pending` | `verified_at IS NULL` и `expires_at > now` |
| `expired` | `verified_at IS NULL` и `expires_at <= now` |
| `verified` | `verified_at IS NOT NULL`, `closed_at IS NULL`, результат доставляется до `verified_at + 15 мин` |
| закрыта | `closed_at IS NOT NULL` — результат использован (первый `RefreshTokens` или `Register`) |

Почему без столбца `status`: `expired` наступает по часам, а не по записи, — столбец пришлось бы обновлять заданием и всё равно сверять с `expires_at`. Альтернатива — `status text` + `CHECK` согласованности со столбцами времени; это дублирование.

Ключевые ограничения:

- **`EXCLUDE USING gist (phone WITH =, tstzrange(created_at, expires_at) WITH &&)`** — «номер занят у провайдера до `expires_at` последней заявки, даже закрытой» (api.md 1.1). Две заявки на номер не пересекаются во времени — гарантия схемы, а не проверка «SELECT, потом INSERT» с гонкой. `INSERT … ON CONFLICT ON CONSTRAINT phone_verification_one_per_phone DO NOTHING RETURNING id` при занятом номере возвращает пустой результат. Цель конфликта указана явно: бесцелевой `ON CONFLICT DO NOTHING` погасил бы и конфликт по хешу токена (`token_hash_key`), и ошибка генератора токенов выглядела бы как «номер занят». Тот же индекс отвечает на вопрос «какая заявка держит номер в момент t» (`retry_at` дубля). Нужно расширение `btree_gist` (доверенное — владелец БД создаёт его без суперпользователя). Down-миграция его **не удаляет**: это инфраструктура БД — up создаёт его только `IF NOT EXISTS`, его может заранее поставить кластер, и тогда `DROP EXTENSION` упал бы на правах владельца и оставил источник `dirty`. Альтернатива — `pg_advisory_xact_lock(hashtext(phone))` + `SELECT … WHERE phone = $1 AND expires_at > $2`; работает, но инвариант держит код.
  - Диапазон полуоткрытый `[created_at, expires_at)`: новая заявка ровно в момент `expires_at` прежней принимается. Провайдер может считать границу иначе — отказ провайдера по дублю при свободном по БД номере уже описан как рассогласование (grpc-api.md 7.1).
  - Порядок шагов 1.1 (ключ идемпотентности → лимиты → занятость) — в коде; схема гарантирует только саму занятость.
- `token_hash UNIQUE` — чтение заявки по хешу токена (1.2, ожидаемый запрос). `registration_token_hash UNIQUE` — `Register` находит заявку по хешу своего токена.
- `UNIQUE (provider, provider_call_id)` — постбэк Zvonok приходит до 5 раз (Confluence, «Подтверждение телефона»): обработка идемпотентна по `call_id`, заявку находит этот индекс. `provider_call_id` пустой, пока провайдер не принял заявку: заявка пишется до вызова провайдера (внешний вызов вне транзакции, `AGENTS.md`), `call_id` дописывается после.
- Согласованность результата: `verified_at` ⇔ `is_new_user`; существующий пользователь ⇒ `user_id`; новый ⇔ `registration_token_hash`; шифротекст ⇔ `result_key_id` и только у подтверждённой; закрытая — без шифротекста и с `user_id` (у нового пользователя — созданный `Register`); `verified_at` внутри `[created_at, expires_at]`; подтверждение только с `provider_call_id`.
- **`LISTEN/NOTIFY`**: триггер `AFTER UPDATE OF verified_at … WHEN (OLD.verified_at IS NULL AND NEW.verified_at IS NOT NULL)` вызывает `pg_notify('phone_verification', id)`. Канал один, полезная нагрузка — внутренний `id` (не телефон и не токен: в `pg_notify` их видит любой слушатель роли). Уведомление уходит при `COMMIT` транзакции вебхука, на любом поде; `WatchPhoneVerification` слушает канал на primary и сверяет `id` своей заявки. Альтернатива — `NOTIFY` из кода вебхука в той же транзакции: без триггера, но легко забыть при втором пути подтверждения (опрос `call_by_id`, фейковый провайдер FIN-122). Триггер выбран, чтобы любой путь подтверждения будил потоки. `expired` уведомления не требует — поток сам знает `expires_at`.
- `provider` — `zvonok`, `fake` (FIN-122) и будущие; открытый код с `CHECK` формата.
- `user_id` → `app_user` `ON DELETE CASCADE`: при удалении аккаунта удаляются заявки с его `user_id`: подтверждённые для существующего пользователя (`user_id` ставит подтверждение) и закрытые `Register` (`user_id` ставит регистрация). Неподтверждённые заявки и подтверждённые для нового пользователя без `Register` `user_id` не имеют и остаются до очистки — см. «Удаление аккаунта (2.5)» и открытый вопрос 6.

### `auth_session`, `refresh_token` — refresh-сессии (1.2, 1.4, 1.5)

Сессия — цепочка ротации; `refresh_token` — её звенья.

- `refresh_token (token_hash)` — PK (SHA-256), `session_id`, `generation` (1, 2, 3…), `issued_at`, `expires_at`, `rotated_at`. Сменённое звено не удаляется до своего `expires_at`: только так предъявленный повторно старый токен узнаётся как **повторное использование**, а не как неизвестный.
- **Одно живое звено на сессию**: `UNIQUE (session_id) WHERE rotated_at IS NULL`. `UNIQUE (session_id, generation)` — порядок звеньев.
- `auth_session.revoked_at` — отзыв всей цепочки при повторном использовании одной записью, а не обновлением всех звеньев. Звенья отозванной сессии отвечают `TOKEN_REVOKED`, пока не истекут.
- `auth_session.phone_verification_id` — заявка, результат которой выдал первое звено; первый `RefreshTokens` по нему закрывает заявку (api.md 1.2). `ON DELETE SET NULL` — очистка старых заявок сессию не трогает.
- **Ротация — одна транзакция** (ожидаемый запрос; проверено `TestRefreshRotationAndReuse` и `TestConcurrentRotationOfOneLink`):

  ```sql
  SELECT r.session_id, r.generation, r.rotated_at, s.revoked_at
  FROM refresh_token r JOIN auth_session s ON s.id = r.session_id
  WHERE r.token_hash = $1 AND r.expires_at > $2
  FOR UPDATE OF r, s;
  -- нет строки          -> INVALID_TOKEN
  -- s.revoked_at        -> TOKEN_REVOKED
  -- r.rotated_at        -> UPDATE auth_session SET revoked_at = $2 WHERE id = …; TOKEN_REVOKED (повтор)
  -- иначе               -> UPDATE refresh_token SET rotated_at = $2 WHERE token_hash = $1;
  --                        INSERT INTO refresh_token (…, generation + 1, …);
  --                        UPDATE phone_verification SET closed_at … (первая ротация)
  ```

  Два параллельных запроса с одним refresh и разными ключами: второй ждёт блокировку строки, затем видит `rotated_at` и отзывает цепочку — так и требует контракт (повтор без того же ключа — повторное использование).
- **Исключение «идемпотентный повтор в течение 60 с»** до этой таблицы не доходит: шаг ключа идемпотентности идёт до проверки токена (api.md, «Ошибки», порядок) и отдаёт сохранённую зашифрованную пару из таблицы библиотеки FIN-78 (срок 60 с). Поэтому в `refresh_token` нет ни «окна 60 с», ни копии нового токена. Эффект (ротация) и запись ключа — в одной транзакции.
- **Выход (1.5)** удаляет сессию (`DELETE FROM auth_session WHERE id = (SELECT session_id FROM refresh_token WHERE token_hash = $1)`), звенья уходят каскадом. Удаление аккаунта — каскадом от `app_user`. Отозванная по повтору сессия остаётся до истечения звеньев (чтобы отвечать `TOKEN_REVOKED`, а не `INVALID_TOKEN`), затем её удаляет очистка.
- Срок refresh (`expires_at`) задаёт сервис; в контракте его нет (открытый вопрос).

### `rate_limit_window` — лимиты (FIN-81, 1.1–1.4)

Счётчики фиксированных окон: `(scope, subject, window_start)` — PK, `window_end`, `hits`. `scope` — лимит и длина окна (`verification_phone_1h`, `verification_ip_1d`, `verification_global_1h`, `watch_ip_1m`, `register_ip_1m`, `refresh_ip_1m`), `subject` — номер, `x-client-ip` или `''` для глобального потолка. Одна попытка — один оператор:

```sql
INSERT INTO rate_limit_window (scope, subject, window_start, window_end, hits)
VALUES ($1, $2, $3, $4, 1)
ON CONFLICT (scope, subject, window_start) DO UPDATE SET hits = rate_limit_window.hits + 1
RETURNING hits;
```

- Только primary («PostgreSQL»: всё, что проверяет «уже было»). Значения лимитов и окна — конфигурация сервиса, не схема.
- «Попытку списывает выполнение, а не воспроизведение» и «429 по лимиту попытку не списывает» (api.md 1.1) — порядок шагов в коде: проверить остаток, затем инкремент в транзакции эффекта (или отдельно для 429 дубля).
- Альтернативы: скользящее окно (журнал попыток с `count(*)` за интервал) — точнее на границе окна, но строка на каждую попытку и подсчёт по диапазону; токен-бакет (`tokens`, `refilled_at`) — одна строка, но вычисления в SQL или в коде под `FOR UPDATE`. Фиксированное окно выбрано как самое простое; если граница окна окажется проблемой — два окна (текущее и предыдущее со взвешиванием) в той же таблице.
- Глобальный потолок FIN-81 — тот же счётчик с `subject = ''`; горячая строка — одна на окно, при порядке десятков заявок в минуту это не узкое место.
- `subject` — номер телефона или адрес, то есть ПДн; живут до `window_end` плюс запас и при удалении аккаунта не стираются (не привязаны к `user_id`). Альтернатива — HMAC ключом сервиса вместо значения: в БД не остаётся номеров, цена — ещё один секрет. Открытый вопрос 8.
- Redis не вводится: лимиты — несколько строк на запрос, PostgreSQL уже есть («Отклонено» — Redis как хранилище).

## Ключи подписи JWT (`GetSigningKeys`)

**Закрытого ключа в БД нет, публичных — тоже; таблицы нет.** «Бэкапы»: ключи подписи JWT — офлайн, отдельно от бэкапов; бэкапы БД не шифруются (принятый риск) — закрытый ключ в БД означал бы ключ в каждом бэкапе на 30 дней PITR.

Предложение (для задачи реализации, не для этой миграции):

- Набор ключей — секрет сервиса файлом (`*_FILE`, как DSN): текущий закрытый Ed25519 с `kid` и список ключей, которые ещё публикуются. JWKS (`GetSigningKeys`) собирается из открытых частей при старте.
- Ротация с перекрытием: (1) новый ключ добавляется только публикуемым; (2) после того как все потребители обновили JWKS (кэш 10 минут, grpc-api.md 7.1) — им начинают подписывать; (3) старый снимается с публикации не раньше чем через срок жизни access-токена (15 минут) плюс кэш. Каждый шаг — смена секрета и перезапуск подов.
- Альтернатива — таблица `signing_key (kid, alg, public_key, not_before, retired_at)` для публичных частей и графика ротации, закрытый ключ — по-прежнему в секрете. Плюс — ротация без перезапуска (под перечитывает таблицу), минус — два источника правды о ключах. Открытый вопрос.

## Удаление аккаунта (2.5)

Одна транзакция `DeleteAccount` на primary:

1. tombstone пользователя (таблица `go-tombstone`, FIN-110);
2. `DELETE FROM app_user WHERE id = $1` — каскадом согласия, заявки с `user_id` (подтверждённые для существующего пользователя и закрытые `Register`), сессии и все refresh (синхронный отзыв);
3. строки outbox `PurgeUserData` для `bank-statement-data`, `analytics`, `assistant` (`go-outbox`, FIN-109).

**Заявки на номер удалённого пользователя без `user_id`** каскад не затрагивает — неподтверждённые (`pending`, `expired`) и подтверждённые для нового пользователя, по которым не было `Register` (с `registration_token_hash` и до 15 минут с `result_ciphertext`): телефон в них остаётся до очистки заявок (открытые вопросы 5 и 6). Это поведение зафиксировано тестом `TestAccountDeletionKeepsPendingRequestsOfThePhone`.

Повтор для удалённого — tombstone найден → OK. Отдельной метки удаления в `app_user` нет (см. «`app_user`»).

Пока библиотеки не выпущены, шаги 1 и 3 подключить нельзя: в `MigrationSources()` они встанут перед источником сервиса, когда у библиотек появятся миграции и теги (`README.md`, «Библиотеки и обновления»).

## Ожидаемые запросы и индексы

## Очистка

Задания сервиса, пачками, не миграции:

- `phone_verification` старше срока хранения (предложение — 24 часа: дольше номер занят быть не может, а результат живёт 15 минут). Хранит номер телефона, поэтому срок — не «навсегда».
- `refresh_token` с `expires_at` в прошлом; сессии без звеньев.
- `rate_limit_window` с `window_end` в прошлом плюс запас.

## Открытые вопросы

1. **Удаление строки `app_user` против мягкого удаления.** Предлагаю удаление строки (выше); подтвердить.
2. **Ключи JWT**: только секрет файлом или таблица публичных ключей с графиком ротации.
3. **Ключ шифрования результата заявки**: отдельный секрет или тот же, которым библиотека идемпотентности шифрует сохранённый ответ `RefreshTokens` (FIN-78). Предлагаю отдельный — у них разные сроки и ротация.
4. **Срок жизни refresh** — в контракте не задан; предлагаю 60 дней скользящим (каждая ротация продлевает), настройкой сервиса.
5. **Срок хранения заявок** для разбора инцидентов и метрики конверсии FIN-81 — 24 часа или дольше (тогда — без номера, обезличенно).
6. **Заявки на номер удаляемого аккаунта.** Две стороны:
   - *остаётся лишнее*: заявки без `user_id` (неподтверждённые и подтверждённые для нового пользователя без `Register`) каскад не удаляет — номер удалённого пользователя лежит в `phone_verification` до очистки (ПДн после «удаления всех данных», 2.5). Варианты: **(а)** в транзакции `DeleteAccount` удалять заявки по номеру — `DELETE FROM phone_verification WHERE phone = $1` (индекс `one_per_phone` по префиксу `phone`); **(б)** принять срок очистки заявок (вопрос 5, предложено 24 часа) и указать его в политике обработки ПДн;
   - *уходит рано*: каскад или вариант (а) удаляют и заявку, которая ещё держит номер у провайдера, — новая заявка в оставшиеся минуты получит отказ провайдера по дублю (путь рассогласования, 429 с `retry_at` + 5 минут). Если это важно — вместо удаления стирать результат и отвязывать (`user_id = NULL`), но тогда номер остаётся до `expires_at` (не дольше 5 минут).

   Решение владельца; схема поддерживает оба варианта без изменений.
7. **Расширение `btree_gist`** создаёт владелец БД (проверено ролью без суперпользователя). Если в CNPG роль сервиса не владеет БД — расширение ставит `postInitApplicationSQL` кластера (FIN-146), а миграция находит его через `IF NOT EXISTS`. Down-миграция расширение не удаляет ни в одном из случаев (решено по ревью PR #2).
8. **ПДн в `rate_limit_window.subject`** — хранить как есть до конца окна или HMAC.
9. **Лимит «по устройству»** из «Аутентификации» в контракте не передаётся (есть только `x-client-ip`); схема его не заводит.
