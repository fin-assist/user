# Схема БД `user`

Задача — [FIN-112](https://finassist.youtrack.cloud/issue/FIN-112). Миграция — [`migrations/000001_init_schema.up.sql`](../migrations/000001_init_schema.up.sql), проверки ключей, каскадов и ожидаемых запросов — [`migrations/schema_test.go`](../migrations/schema_test.go). Смысл полей — `fin-assist/contracts`: `docs/api.md` 1–2, `docs/grpc-api.md` 6, 6.1, 7.1; решения — Confluence PF «Архитектура» («Аутентификация», «Идемпотентность», «Идентификаторы», «PostgreSQL», «Бэкапы»).

Схема — предложение, принятое владельцем по ревью PR #2: решения ниже с аргументами и альтернативами, решения по вопросам — в конце (все закрыты 19.10.2026).

**Решение владельца 19.10.2026 (ревью PR #2):** в БД нет правил валидации и логики. В схеме — только `PRIMARY KEY`, `UNIQUE` (в том числе частичные уникальные индексы), `FOREIGN KEY` с каскадами, `NOT NULL` и `DEFAULT` (в том числе `uuidv7()`, `now()`). Нет `CHECK`, `EXCLUDE`, триггеров и функций; форматы, диапазоны, согласованность состояний и уведомления — код сервиса (раздел «Инварианты в коде сервиса»). `TestSchemaHasNoRulesOrLogic` не даёт новой миграции вернуть их незаметно.

## Общие правила

- **Секреты не хранятся в открытом виде.** `verification_token`, `registration_token`, refresh — 256 случайных бит, в БД только SHA-256 (`bytea`, 32 байта — длину обеспечивает код). Соль и медленный хеш не нужны: перебор 2²⁵⁶ невозможен, а поиск по хешу — точное совпадение по уникальному индексу. Сравнение «за постоянное время» (api.md 1.2) обеспечивает именно поиск по хешу: время зависит от хеша, а не от совпавшего префикса токена.
- **Результат для повторной доставки** (пара токенов существующего пользователя или `registration_token` нового — 15 минут с подтверждения, api.md 1.2) по хешу не восстановить, поэтому он хранится шифротекстом ключа сервиса (AES-GCM, `result_key_id` — какой ключ) и стирается при закрытии заявки или по истечении 15 минут. Ключ — отдельный секрет сервиса (не общий с ключом шифрования ответа `RefreshTokens` в FIN-78: разные сроки и ротация; решение владельца 19.10.2026, вопрос 3), не в БД.
- **Ключи подписи JWT в БД нет** (ниже).
- **Время бизнес-правил пишет сервис** из внедрённых часов (`AGENTS.md`, Time): `expires_at`, `verified_at`, `released_at`, `rotated_at`, `revoked_at`, `granted_at`, `updated_at`. `now()` по умолчанию — только у технических `created_at` и у начального `updated_at`.
- **ID** («Идентификаторы»): `app_user.id` выходит за пределы БД — `uuid` UUIDv7 (`uuidv7()` PostgreSQL 18). Остальные ID внутренние — `integer GENERATED ALWAYS AS IDENTITY`: ширина по числу вставок за жизнь таблицы. Самая быстрорастущая — `phone_verification` (заявка на каждый вход): 2,1 млрд заявок — это порядка 600 млн ₽ звонков по тарифу Zvonok, раньше упрёмся в бюджет FIN-81. Сессии — по одной на вход, согласия — единицы на пользователя. `settings_version`, `generation`, `hits` — тоже `integer`. Правило squawk `prefer-bigint-over-int` выключено в `.squawk.toml` с этим обоснованием (ревью PR #2).
- **Тексты-коды** (`theme`, тип согласия, `provider`) — `text`, а не `enum` PostgreSQL: допустимые значения знает код (и контракт), новое значение не требует миграции, а значение `enum` нельзя удалить.
- **Таблицы библиотек** (outbox FIN-109, идемпотентность FIN-78, tombstone FIN-110) здесь не создаются: у библиотек свои источники миграций и таблицы версий (`docs/migrations.md`). Сейчас библиотеки — каркасы без миграций и тегов, поэтому в `MigrationSources()` они появятся вместе с их выпуском.

## Сущности

### `consent_document` — документы согласий (1.6)

- `consent_document (type, version)` — PK; `title`, `url`. Новая версия — новая строка, старые остаются: на них ссылаются данные согласия.
- **Текущая версия — флаг `is_current boolean NOT NULL DEFAULT false`** и частичный уникальный индекс `consent_document_current_key ON (type) WHERE is_current`: не больше одной текущей версии на тип, тот же индекс находит её по типу. Решение владельца 20.10.2026 (тред ревью «Зачем эта таблица?», вариант 1) — вместо отдельной таблицы `consent_current`.
- **Смена текущей версии** — миграция данных, одна транзакция (файл миграции и так атомарен), порядок важен из-за индекса: сначала снять флаг со старой, затем поставить новой:

  ```sql
  INSERT INTO consent_document (type, version, title, url) VALUES ('assistant', '2026-11-01', …, …);
  UPDATE consent_document SET is_current = false WHERE type = 'assistant' AND is_current;
  UPDATE consent_document SET is_current = true  WHERE type = 'assistant' AND version = '2026-11-01';
  ```

  Обратный порядок падает на `consent_document_current_key` на первом же `UPDATE` (проверка уникальности — по строке, не в конце транзакции). Что текущая версия у типа есть всегда — правило кода и миграций данных (строка 12 «Инвариантов»), схема держит только «не больше одной». Тесты — `TestCurrentConsentDocument`.
- Наполняются миграцией данных (новая версия документа — новый файл миграции): документы меняют юристы и релизом, а не пользователи. Альтернатива — конфигурация сервиса; минус — версии в БД нужны для внешних ключей `user_consent`.
- `type` — открытый код (`personal_data`, `assistant`), а не закрытый список: новый тип согласия — новая строка (`consents[]` списком, FIN-82).
- **Зачем версии** (вопрос владельца на ревью). Версия — поле контракта: клиент передаёт `pd_consent_version` / `version` (1.3, 2.3), сервер отвечает `CONSENT_OUTDATED` на устаревшую, профиль отдаёт `version` и `current_version` (2.1), чтобы попросить согласие заново после смены текста. Согласие на обработку ПДн по 152-ФЗ доказывается конкретным текстом, который видел человек: без строки «версия → url» в БД не восстановить, на что он согласился год назад. Поэтому старые версии остаются, а `user_consent` ссылается на них внешним ключом.

### `app_user` — пользователь и профиль (2.1–2.2)

| Столбец | Зачем |
|---|---|
| `id uuid` | UUIDv7, `user_id` во всех сервисах |
| `phone text` | E.164 (api.md 1.1: только `+7` и 10 цифр — проверяет код); `UNIQUE` |
| `theme text` | `system` / `light` / `dark` — проверяет код |
| `timezone text` | IANA, по умолчанию `Europe/Moscow` (1.3); корректность имени проверяет сервис по базе поясов Go — той же, по которой считают потребители, а не `pg_timezone_names` |
| `settings_version integer` | версия настроек для `SetUserTimezone` (grpc-api.md 6.1, поле контракта): `UPDATE … SET timezone = $2, settings_version = settings_version + 1, updated_at = $3 … RETURNING settings_version` и строка outbox в той же транзакции. Зачем (вопрос владельца на ревью): outbox доставляет at-least-once и без порядка, а получателей два (`bank-statement-data`, `assistant`); при двух сменах пояса подряд старое событие может прийти позже нового, и получатель без версии откатил бы пояс. Получатель применяет только большую версию. Время вместо версии хуже: два изменения в одну миллисекунду и часы разных подов |
| `created_at` | дата регистрации (2.1) |
| `updated_at` | последнее изменение профиля (тема, пояс); ставит код при каждом `UPDATE` (по ревью). На других таблицах не нужен: документы согласий меняет только миграция данных; момент смены текущей версии в БД не хранится (таблица версий golang-migrate держит только `version` и `dirty`) — он виден по коммиту и дате файла миграции данных в git, а доказательство согласия от него не зависит: оно в `user_consent.version` и `granted_at`, а у остальных изменение — событие со своим временем (`revoked_at`, `verified_at`, `closed_at`, `released_at`, `rotated_at`) |

**«Телефон уникален среди живых пользователей» — простой `UNIQUE (phone)`, потому что удалённого пользователя в таблице нет.** Удаление аккаунта удаляет строку `app_user`, внешние ключи с `ON DELETE CASCADE` удаляют согласия, заявки с его `user_id` (подтверждённые для существующего пользователя и закрытые `Register`) и сессии (refresh); остальные заявки на его номер `user_id` не имеют, их `DeleteAccount` удаляет по номеру в той же транзакции (вопрос 6, решение владельца). Что `user_id` удалён, помнит tombstone библиотеки (FIN-110) — в нём только `user_id` и момент удаления, без ПДн («Аутентификация»).

**Имя `app_user`, а не `user`** — решение владельца 19.10.2026 (ревью PR #2): `user` — зарезервированное слово SQL, `SELECT user` возвращает текущую роль, и имя таблицы пришлось бы везде брать в кавычки (`"user"`) — забытые кавычки дают не ошибку, а другой смысл.

Альтернатива — мягкое удаление (`deleted_at`) с частичным `UNIQUE (phone) WHERE deleted_at IS NULL`. Отклонил: строка с телефоном удалённого пользователя — это ПДн, которые нужно стирать отдельно (152-ФЗ, «удаляет все данные»), а любой новый запрос обязан помнить `WHERE deleted_at IS NULL`. Плюс удаления строки — опоздавшая запись (транзакция, прочитавшая пользователя до удаления) падает на внешнем ключе, а не воскрешает данные: это и есть защита FIN-110, п. 5, для таблиц `user`.

### `user_consent` — согласия пользователя (`consents[]`, 1.3, 2.3, 2.4)

- Строка на одну выдачу согласия: `type`, `version` (внешний ключ на документ), `granted_at`, `revoked_at`. История остаётся: отзыв ставит `revoked_at`, повторная выдача — новая строка.
- **Одно действующее согласие на тип**: `UNIQUE (user_id, type) WHERE revoked_at IS NULL`. Тот же индекс с `INCLUDE (version)` отвечает `GetAssistantConsentStatus` index-only сканом без чтения истории.
- Согласие на ПДн из 1.3 — строка `personal_data` при регистрации, в одной транзакции с `app_user`. В `consents[]` профиля оно не входит (api.md 2.1) — это фильтр чтения, а не схемы.
- **Зачем отдельная таблица** (вопрос владельца на ревью), а не столбцы в `app_user`: согласий несколько типов, и набор растёт — контракт отдаёт `consents[]` списком и прямо запрещает «поле на каждую сущность» (FIN-82); столбцы `assistant_consent_version`, `assistant_consent_at`… пришлось бы добавлять миграцией на каждый новый тип. Кроме того, нужна история (дал — отозвал — дал заново по новой версии): доказательство согласия на момент обработки данных. Обращение `GetAssistantConsentStatus` — один index-only скан, как и при столбцах.
- PK `(user_id, id)` — `user_id` первым, как в остальных сервисах (Confluence «Хранение данных»: `user_id` в каждом первичном ключе).
- «Устаревшая версия → `CONSENT_OUTDATED`» — проверка сервиса (присланная версия = версия с `is_current` того же типа), а не схемы: в истории законно лежат старые версии.

### `phone_verification` — заявки на верификацию (1.1–1.3)

Состояния — производные от столбцов, без отдельного `status`:

| Состояние | Условие |
|---|---|
| `pending` | `verified_at IS NULL` и `expires_at > now` |
| `expired` | `verified_at IS NULL` и `expires_at <= now` |
| `verified` | `verified_at IS NOT NULL`, `closed_at IS NULL`, результат доставляется до `verified_at + 15 мин` |
| закрыта | `closed_at IS NOT NULL` — результат использован (первый `RefreshTokens` или `Register`) |

Почему без столбца `status`: `expired` наступает по часам, а не по записи, — столбец пришлось бы обновлять заданием и всё равно сверять с `expires_at`.

Отдельно от состояния — **держит ли заявка номер** (`released_at IS NULL`): у провайдера номер занят до `expires_at` заявки, даже закрытой (ниже).

Ключевые ограничения:

- **Одна заявка держит номер — частичный уникальный индекс** `phone_verification_phone_held_key ON (phone) WHERE released_at IS NULL` («номер занят у провайдера до `expires_at` последней заявки, даже закрытой», api.md 1.1). Предикат индекса не может зависеть от `now()`, поэтому освобождение — отдельный столбец `released_at`, который ставит код. Не `closed_at`: закрытие — «результат использован» (первый `RefreshTokens` / `Register`) и наступает раньше `expires_at`, а номер у провайдера остаётся занятым до `expires_at`; совместить их — потерять один из смыслов. Создание заявки — одна транзакция:

  ```sql
  -- освободить держателя, срок которого прошёл
  UPDATE phone_verification SET released_at = $now
  WHERE phone = $1 AND released_at IS NULL AND expires_at <= $now;
  -- занять номер; пусто — номер занят
  INSERT INTO phone_verification (phone, token_hash, provider, created_at, expires_at)
  VALUES ($1, $2, $3, $now, $now + interval '5 minutes')
  ON CONFLICT (phone) WHERE released_at IS NULL DO NOTHING
  RETURNING id;
  -- если пусто: retry_at дубля — expires_at держателя, по тому же индексу
  SELECT expires_at FROM phone_verification WHERE phone = $1 AND released_at IS NULL;
  ```

  Параллельные создания на один номер сериализует сам уникальный индекс: вторая транзакция ждёт на нём первую и после её `COMMIT` получает пустой `RETURNING` (`TestConcurrentVerificationsOfOnePhone`, 8 транзакций — ровно одна заявка). Advisory-lock не нужен. Если после пустого `INSERT` держатель не найден (его удалил `DeleteAccount` по номеру между операторами — раздел «Удаление аккаунта»), сценарий повторяет освобождение и вставку, а не отвечает ошибкой; число повторов ограничено (например, тремя), дальше — внутренняя ошибка. Путь на уровне схемы проверяет `TestVerificationRetryWhenTheHolderIsDeletedByPhone`. Цель конфликта указана явно: бесцелевой `ON CONFLICT DO NOTHING` погасил бы и конфликт по хешу токена, и ошибка генератора токенов выглядела бы как «номер занят» (тест есть). Держатель с прошедшим сроком, которого никто не освободил (на номер больше не входили), номера не блокирует: его освобождает следующая заявка на этот номер или задание очистки. Граница: новая заявка ровно в момент `expires_at` прежней принимается; отказ провайдера по дублю при свободном по БД номере — рассогласование (grpc-api.md 7.1). Порядок шагов 1.1 (ключ идемпотентности → лимиты → занятость) — в коде. Расширение `btree_gist` прежнего варианта (`EXCLUDE`) больше не нужно.
- `token_hash UNIQUE` — чтение заявки по хешу токена (1.2, ожидаемый запрос). `registration_token_hash UNIQUE` — `Register` находит заявку по хешу своего токена.
- `UNIQUE (provider, provider_call_id)` — постбэк Zvonok приходит до 5 раз (Confluence, «Подтверждение телефона»): обработка идемпотентна по `call_id`, заявку находит этот индекс. `provider_call_id` пустой, пока провайдер не принял заявку: заявка пишется до вызова провайдера (внешний вызов вне транзакции, `AGENTS.md`), `call_id` дописывается после.
- Согласованность результата (подтверждённая ⇔ исход, у существующего — `user_id`, у нового — хеш `registration_token`, шифротекст только у подтверждённой и только до закрытия и т. д.) — код, см. «Инварианты в коде сервиса».
- **`LISTEN/NOTIFY`**: транзакция, которая подтверждает заявку (постбэк, опрос `call_by_id`, фейковый провайдер FIN-122), сама вызывает `SELECT pg_notify('phone_verification', $id)`. Уведомление уходит только при `COMMIT` (откат — без уведомления, `TestVerificationNotifiesOnCommit`), на любом поде; `WatchPhoneVerification` слушает канал на primary и сверяет `id` своей заявки. Канал один, полезная нагрузка — внутренний `id` (не телефон и не токен: в `pg_notify` их видит любой слушатель роли). Чтобы путь подтверждения не забыл уведомить, запись подтверждения и `pg_notify` — один метод репозитория. Раньше это был триггер; убран по решению владельца (в БД нет логики). `expired` уведомления не требует — поток сам знает `expires_at`.
- `provider` — `zvonok`, `fake` (FIN-122) и будущие; открытый код.
- `user_id` → `app_user` `ON DELETE CASCADE`: при удалении аккаунта удаляются заявки с его `user_id`: подтверждённые для существующего пользователя (`user_id` ставит подтверждение) и закрытые `Register` (`user_id` ставит регистрация). Неподтверждённые заявки и подтверждённые для нового пользователя без `Register` `user_id` не имеют — их `DeleteAccount` удаляет по номеру (`phone_verification_phone_idx`), см. «Удаление аккаунта (2.5)» и вопрос 6.

### `auth_session`, `refresh_token` — refresh-сессии (1.2, 1.4, 1.5)

Сессия — цепочка ротации; `refresh_token` — её звенья.

- `refresh_token (token_hash)` — PK (SHA-256), `session_id`, `generation` (1, 2, 3…), `issued_at`, `expires_at`, `rotated_at`. Сменённое звено не удаляется до своего `expires_at`: только так предъявленный повторно старый токен узнаётся как **повторное использование**, а не как неизвестный.
- **Одно живое звено на сессию**: `UNIQUE (session_id) WHERE rotated_at IS NULL`. `UNIQUE (session_id, generation)` — порядок звеньев. `auth_session.id` и `generation` — `integer`.
- `auth_session.revoked_at` — отзыв всей цепочки при повторном использовании одной записью, а не обновлением всех звеньев. Звенья отозванной сессии отвечают `TOKEN_REVOKED`, пока не истекут.
- `auth_session.phone_verification_id` — заявка, результат которой выдал первое звено; первый `RefreshTokens` по нему закрывает заявку (api.md 1.2). `ON DELETE SET NULL` — очистка старых заявок сессию не трогает.
- **Ротация — одна транзакция** (ожидаемый запрос; проверено `TestRefreshRotationAndReuse` и `TestConcurrentRotationOfOneLink`):

  ```sql
  SELECT r.session_id, r.generation, r.rotated_at, s.revoked_at
  FROM refresh_token r JOIN auth_session s ON s.id = r.session_id
  WHERE r.token_hash = $1 AND r.expires_at > $2
  FOR UPDATE OF r, s;
  -- нет строки          -> INVALID_TOKEN
  -- s.revoked_at        -> TOKEN_REVOKED
  -- r.rotated_at        -> UPDATE auth_session SET revoked_at = $2 WHERE id = …; TOKEN_REVOKED (повтор)
  -- иначе               -> UPDATE refresh_token SET rotated_at = $2 WHERE token_hash = $1;
  --                        INSERT INTO refresh_token (…, generation + 1, …);
  --                        UPDATE phone_verification SET closed_at … (первая ротация)
  ```

  Два параллельных запроса с одним refresh и разными ключами: второй ждёт блокировку строки, затем видит `rotated_at` и отзывает цепочку — так и требует контракт (повтор без того же ключа — повторное использование).
- **Исключение «идемпотентный повтор в течение 60 с»** до этой таблицы не доходит: шаг ключа идемпотентности идёт до проверки токена (api.md, «Ошибки», порядок) и отдаёт сохранённую зашифрованную пару из таблицы библиотеки FIN-78 (срок 60 с). Поэтому в `refresh_token` нет ни «окна 60 с», ни копии нового токена. Эффект (ротация) и запись ключа — в одной транзакции.
- **Выход (1.5)** удаляет сессию (`DELETE FROM auth_session WHERE id = (SELECT session_id FROM refresh_token WHERE token_hash = $1)`), звенья уходят каскадом. Удаление аккаунта — каскадом от `app_user`. Отозванная по повтору сессия остаётся до истечения звеньев (чтобы отвечать `TOKEN_REVOKED`, а не `INVALID_TOKEN`), затем её удаляет очистка.
- Срок refresh (`expires_at`) — 60 дней скользящим: каждая ротация выдаёт звено с новым сроком; значение — настройка сервиса (решение владельца 19.10.2026, вопрос 4).

### `rate_limit_window` — лимиты (FIN-81, 1.1–1.4)

Счётчики фиксированных окон: `(scope, subject, window_start)` — PK, `window_end`, `hits`.
В реализации FIN-219 `scope` — имя политики и длина окна в секундах (`watch_ip:60`),
`subject` — телефон или доверенный `x-client-ip`. Глобальный потолок с `subject = ''`
остаётся FIN-81. Схема не меняется. Для нескольких окон сначала блокируются все строки
в стабильном порядке scope, без увеличения hits:

```sql
INSERT INTO rate_limit_window (scope, subject, window_start, window_end, hits)
VALUES ($1, $2, $3, $4, 0)
ON CONFLICT (scope, subject, window_start) DO UPDATE SET hits = rate_limit_window.hits
RETURNING hits;
```

Если хотя бы один счётчик достиг предела, ни один не увеличивается. Иначе все hits
увеличиваются на 1 в той же primary-транзакции. Это предотвращает частичное списание
при исчерпанном другом окне и сериализует гонку на отсутствующей строке. Ошибка или
откат последующего эффекта откатывает все счётчики. Подробности и момент учёта метрик —
[limits.md](limits.md); `TestLimitsMultipleWindowsAndReset`,
`TestLimitsConcurrentAttemptsCanonicalIPAndScopes`, `TestLimitsRollbackDurationChangeAndFailures`.

- Только primary («PostgreSQL»: всё, что проверяет «уже было»). Значения лимитов и окна — конфигурация сервиса, не схема.
- «Попытку списывает выполнение, а не воспроизведение» и «429 по лимиту попытку не списывает» (api.md 1.1) — порядок шагов в коде: проверить остаток, затем инкремент в транзакции эффекта (или отдельно для 429 дубля).
- Альтернативы: скользящее окно (журнал попыток с `count(*)` за интервал) — точнее на границе окна, но строка на каждую попытку и подсчёт по диапазону; токен-бакет (`tokens`, `refilled_at`) — одна строка, но вычисления в SQL или в коде под `FOR UPDATE`. Фиксированное окно выбрано как самое простое; если граница окна окажется проблемой — два окна (текущее и предыдущее со взвешиванием) в той же таблице.
- Глобальный потолок FIN-81 — тот же счётчик с `subject = ''`; горячая строка — одна на окно, при порядке десятков заявок в минуту это не узкое место.
- `subject` — номер телефона или адрес, то есть ПДн; живут до `window_end` плюс запас и при удалении аккаунта не стираются (не привязаны к `user_id`). Хранится текстом, не HMAC — решение владельца 19.10.2026 (вопрос 8).
- **Зачем отдельная таблица** (вопрос владельца на ревью), а не подсчёт по `phone_verification`: (1) лимиты считают и попытки, которые заявку не создают — 429 на занятый номер засчитывается (api.md 1.1), а `WatchPhoneVerification`, `Register` и `RefreshTokens` ограничиваются по `x-client-ip` вообще без строк в других таблицах; (2) `x-client-ip` в заявке не хранится и хранить его там незачем; (3) подсчёт `count(*)` по заявкам за окно — сканирование диапазона на каждый запрос вместо одной строки. Счётчик в памяти пода не годится: подов три, лимит делился бы между ними.
- Redis не вводится: лимиты — несколько строк на запрос, PostgreSQL уже есть («Отклонено» — Redis как хранилище).

## Ключи подписи JWT (`GetSigningKeys`)

**Закрытого ключа в БД нет, публичных — тоже; таблицы нет.** «Бэкапы»: ключи подписи JWT — офлайн, отдельно от бэкапов; бэкапы БД не шифруются (принятый риск) — закрытый ключ в БД означал бы ключ в каждом бэкапе на 30 дней PITR.

Решение владельца 19.10.2026 (вопрос 2) — секрет файлом, таблицы ключей нет:

- Набор ключей — секрет сервиса файлом (`*_FILE`, как DSN): текущий закрытый Ed25519 с `kid` и список ключей, которые ещё публикуются. JWKS (`GetSigningKeys`) собирается из открытых частей при старте.
- Ротация с перекрытием: (1) новый ключ добавляется только публикуемым; (2) после того как все потребители обновили JWKS (кэш 10 минут, grpc-api.md 7.1) — им начинают подписывать; (3) старый снимается с публикации не раньше чем через срок жизни access-токена (15 минут) плюс кэш. Каждый шаг — смена секрета и перезапуск подов.
- Отклонено: таблица `signing_key` для публичных частей и графика ротации (ротация без перезапуска, но два источника правды о ключах).

## Удаление аккаунта (2.5)

Одна транзакция `DeleteAccount` на primary:

1. tombstone пользователя (таблица `go-tombstone`, FIN-110);
2. `DELETE FROM app_user WHERE id = $1` — каскадом согласия, заявки с `user_id` (подтверждённые для существующего пользователя и закрытые `Register`), сессии и все refresh (синхронный отзыв);
3. `DELETE FROM phone_verification WHERE phone = $1` — все остальные заявки номера (решение владельца 19.10.2026, вопрос 6, вариант (а)); индекс `phone_verification_phone_idx`;
4. строки outbox `PurgeUserData` для `bank-statement-data`, `analytics`, `assistant` (`go-outbox`, FIN-109).

**Заявки на номер удалённого пользователя без `user_id`** — неподтверждённые (`pending`, `expired`) и подтверждённые для нового пользователя без `Register` (с `registration_token_hash` и до 15 минут с `result_ciphertext`) — каскад не затрагивает, поэтому шаг 3 удаляет их по номеру: после удаления аккаунта номера нет ни в одной таблице сервиса, кроме `rate_limit_window` (вопрос 8). Заявки других номеров не затрагиваются — `TestAccountDeletionRemovesAllRequestsOfThePhone`. Следствие: удаляется и заявка, которая ещё держит номер у провайдера; новая заявка на этот номер в оставшиеся минуты пройдёт по БД, а провайдер откажет по дублю — путь рассогласования (429 с `retry_at` + 5 минут, grpc-api.md 7.1). Вариант «отвязывать вместо удаления» отклонён.

Повтор для удалённого — tombstone найден → OK. Отдельной метки удаления в `app_user` нет (см. «`app_user`»).

go-tombstone v0.1.0 и go-outbox v0.1.0 подключены, их миграции стоят перед источником
сервиса. Сам DeleteAccount и события PurgeUserData остаются следующим этапом FIN-219.
Текущий профильный этап использует Guard библиотеки tombstone и события смены пояса.

Профиль/согласие читаются одним SELECT с LEFT JOIN активного user_consent и текущего
consent_document. Системный статус и пишущие операции используют primary. Записи берут
Guard и FOR UPDATE app_user; смена пояса и outbox атомарны, повтор того же значения
не увеличивает settings_version. Действующим считается согласие на текущую версию;
отзыв и повтор выдачи сохраняют историю. Реализация и тесты — internal/profile,
internal/adapter/postgres/profile.go, TestProfilesSettingsOutboxAndPrimaryReads,
TestProfilesConsentHistoryAndVersionSwitch, TestProfilesRollbackConcurrencyAndDeletion.

## Инварианты в коде сервиса

По решению владельца 19.10.2026 в схеме нет `CHECK`, `EXCLUDE`, триггеров и функций. Что раньше держала схема и как это обеспечит код. Каждая строка — юнит-тест функции домена или сценария и, где нужна БД, интеграционный тест репозитория (вместе с кодом, не в этом PR).

| # | Инвариант | Где в коде |
|---|---|---|
| 1 | Телефон — E.164, `+7` и 10 цифр (api.md 1.1) | protovalidate в контракте на входе; домен — тип номера с конструктором, который отклоняет иное; в БД номер попадает только через этот тип |
| 2 | Токены — 256 случайных бит; в БД только SHA-256, 32 байта (`token_hash`, `registration_token_hash`, `refresh_token.token_hash`) | один пакет: `NewToken()` (crypto/rand) и `Hash(token) [32]byte`; репозитории принимают `[32]byte`, а не `[]byte` — неверная длина не компилируется |
| 3 | Согласованность заявки: подтверждена ⇔ есть `is_new_user`; существующий пользователь ⇒ `user_id`; новый ⇔ хеш `registration_token`; шифротекст ⇔ `result_key_id`, только у подтверждённой, стирается при закрытии; закрытая ⇒ подтверждена и `closed_at ≥ verified_at`, у нового — `user_id` от `Register`; подтверждение только с `provider_call_id` и в срок `[created_at, expires_at]` | переходы состояний — методы сущности домена (`Verify`, `Close`, `Release`), каждый пишет весь набор столбцов одним `UPDATE … WHERE` с условием исходного состояния (`verified_at IS NULL`, `closed_at IS NULL`); `RowsAffected = 0` — переход не применён (повтор постбэка, гонка) |
| 4 | Одна заявка держит номер | **в схеме** — частичный `UNIQUE (phone) WHERE released_at IS NULL`; код освобождает держателя с прошедшим `expires_at` в транзакции создания (раздел заявок); «держатель не найден» после пустой вставки — повтор, не ошибка. Сериализацию даёт индекс, advisory-lock не нужен |
| 5 | `expires_at > created_at`, срок 5 минут | `expires_at` вычисляет только сценарий 1.1 из часов: `now + 5m` |
| 6 | Подтверждение будит `WatchPhoneVerification` | метод репозитория «подтвердить» в той же транзакции вызывает `pg_notify('phone_verification', id)`; другого способа записать `verified_at` у репозитория нет |
| 7 | После удаления аккаунта не остаётся заявок на его номер (вопрос 6) | `DeleteAccount` в своей транзакции: `DELETE FROM app_user` (каскад) и `DELETE FROM phone_verification WHERE phone = $1`; номер берётся из строки `app_user`, прочитанной `FOR UPDATE` в начале той же транзакции |
| 8 | Тема — `system`/`light`/`dark` | enum контракта `Theme` на входе (закрытый набор, api.md 2.2), в БД пишет код по таблице соответствия |
| 9 | Пояс — существующее имя IANA, не длиннее 64 | `time.LoadLocation` при `Register` и `UpdateProfile` (та же база поясов Go, что у потребителей) |
| 10 | `settings_version` растёт на 1 при каждой смене пояса | `UPDATE … SET settings_version = settings_version + 1 … RETURNING` в одной транзакции со строкой outbox |
| 11 | `revoked_at ≥ granted_at` у согласия; версия согласия — текущая (`CONSENT_OUTDATED`) | сценарии `GrantAssistantConsent`, `RevokeAssistantConsent`, `Register`: время из часов, версия сверяется с текущей (`consent_document … WHERE type = $1 AND is_current`) в той же транзакции |
| 12 | Документ согласия: `url` — `https://`, не длиннее 2000; `title` — от 1 до 500 символов; формат `type` и `version`; у каждого типа, который читает сервис, есть ровно одна текущая версия (схема держит «не больше одной») | документы приходят только миграцией данных; тест миграций данных проверяет все строки `consent_document` (появится с первой версией документа) |
| 13 | Звено refresh: `generation > 0`, `expires_at > issued_at`, `rotated_at ≥ issued_at` | звенья пишет только сценарий выдачи (`generation = 1`) и ротации (`generation + 1`, время из часов) |
| 14 | `provider`, `result_key_id`, `scope` лимита — известные значения | константы в коде; `provider` — имя реализации интерфейса провайдера, `scope` — из конфигурации лимитов |
| 15 | Счётчик лимита: `hits > 0`, `window_end > window_start`, `subject` ≤ 64 | единственный `INSERT … ON CONFLICT DO UPDATE` счётчика; окно вычисляет функция домена |
| 16 | `provider_call_id` — 1…128 символов. Внешний недоверенный ввод: приходит из ответа API и постбэка провайдера, а не из запроса клиента и не из констант | адаптер провайдера отклоняет пустое или длиннее 128 значение как ошибку рассогласования (лог и метрика, как отказ по дублю); в БД попадает только проверенное значение. Иначе пустые `call_id` сталкивались бы на `phone_verification_provider_call_key`, а значение в несколько КБ ломало бы вставку в индекс (bare `INTERNAL`) |

Что осталось в схеме: первичные ключи, уникальность (телефон пользователя, одно действующее согласие на тип, одна текущая версия документа на тип, одна заявка держит номер, хеши токенов, `call_id`, одно живое звено refresh, поколение звена), внешние ключи с каскадами (удаление аккаунта, ссылки на версии документов, очистка заявок), `NOT NULL`, значения по умолчанию.

- `phone_verification` старше 24 часов (решение владельца 19.10.2026, вопрос 5: дольше номер занят быть не может, а результат живёт 15 минут). Хранит номер телефона, поэтому срок — не «навсегда».
