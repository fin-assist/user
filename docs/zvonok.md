# Zvonok V1: подтверждение телефона

FIN-139 и FIN-216 подключают реального провайдера к общему Start/Confirm/Watch.
API V1 выбран по ответу поддержки 23.10.2026: `pincode_incoming` не поддерживается V2.
Источники: [официальная спецификация](https://api.zvonok.com/) (вкладка V1),
[примеры V1](https://api-docs.zvonok.com/), ответы поддержки в FIN-139 и решения FIN-219.

## Активация и секреты

По умолчанию `PHONE_PROVIDER=disabled`. Для dev/stage нужны `PHONE_PROVIDER=zvonok`,
`ZVONOK_PUBLIC_KEY_FILE` (systemd credential / mounted secret), `ZVONOK_CAMPAIGN_ID`.
Значение ключа не передают в чате, CLI-аргументах и git. Весь ответ провайдера,
HTTP URL, ошибки net/http и тела multipart не логируются. Нет настройки произвольного
API URL: endpoint фиксирован `https://zvonok.com/manager/cabapi_external/api/v1/`.
Редиректы запрещены, ответ ограничен 1 МиБ, HTTP-запрос — 3 секундами и контекстом.

Исключение владельца 24.10.2026: документированные GET `calls_by_phone`, `call_by_id`
передают `public_key` в query. Клиент не выпускает наружу URL даже при сетевой ошибке.
Создание — только POST `phones/confirm/`, ключ, кампания и телефон в multipart-теле.
Кампания выделена сервису; другие приложения/операторы не добавляют в неё звонки.
У всех реплик один ключ. API-слоты общие в PostgreSQL, включая чтения и повторы:
20 за UTC-секунду на ключ, ожидание до конца окна ограничено контекстом запроса.
Нет транзакции или занятого соединения во время HTTP/ожидания следующего окна.
Внешний 429 всё равно обрабатывается: лимит API не является нашим денежным бюджетом.

**Prod не включается до FIN-81**: конфигурация отклоняет Zvonok при `ENV=prod`.
Фейковый провайдер, публикация документов согласий, инфраструктурная настройка ingress
и реальная приёмка кампании не подменяются этой интеграцией.

## Создание и восстановление

Перед новым confirm клиент читает историю телефона в своей кампании. Старый
незавершённый звонок — рассогласование/дубль, он не выдаётся новому клиентскому ключу.
Ошибка до первого confirm не создаёт внешний эффект и разрешает возврат резерва.
Явный отказ первого confirm (429 или JSON error при 4xx) также разрешает возврат.
Отказ повторного confirm при Recover не доказывает отказ исходной попытки: её
резерв сохраняется, даже если повтор получил 429/4xx. Сеть, 5xx,
повреждённый/слишком большой ответ, пустой пул — неопределённый исход, без возврата:
только общий Starter может атомарно вернуть лимит после ReleaseIfCurrent.

Recover читает статус по известному call_id либо историю своей durable-попытки.
Телефон, ID и время создания проверяются; несколько подходящих звонков, чужой номер,
неизвестный нетерминальный статус или невозможность установить владельца запрещают
повтор confirm. Консервативная проверка времени требует синхронизированных часов
сервиса и провайдера; расхождение приводит к отказу, а не принятию чужой заявки.
Пустая история позволяет повторить добавление своей попытки. Если в ответ вернулся
старый звонок, срок не продлевается, даже если история временно его не показала.

Поддержка гарантирует: повтор confirm незавершённого звонка возвращает прежний ID и
его прежние allowed_phones_for_call. После терминального статуса появляется новый ID.
Гонка статус → confirm обрабатывается по фактическому ID/времени ответа: новый звонок
получает новый полный срок 5 минут, старое подтверждение к нему не переносится.
Вызовы remove_call не нужны. Старый пул никогда не используется для нового звонка.

Пул — 1–1000 различных E.164 номеров. `crypto/rand.Int` равномерно выбирает один;
selector сохраняет список и выбор в phone_verification внутри транзакции завершения
Start. Повтор ключа возвращает сохранённый выбор. Если транзакция откатилась, её
секрет/выбор клиенту не выдавались и повтор может выбрать заново из свежего ответа.

## Постбэк и Watch

Отдельный HTTP-listener `ZVONOK_CALLBACK_ADDR` (по умолчанию :9095), единственный маршрут
`GET /callbacks/zvonok`. Ops остаётся :9091; маршрут не проходит через bank-bff.
В кампании URL настраивают с ct_call_id, ct_phone, ct_status и ct_dial_status.
IP провайдера — 193.232.64.150. Сам сервис также проверяет источник: RemoteAddr,
либо цепочку X-Forwarded-For справа налево только от явно настроенных
`ZVONOK_TRUSTED_PROXY_CIDRS`. Не задавать широкие сети всех клиентов. Ingress должен
перезаписывать заголовки, ограничивать источник и не писать query в access/error log:
там может быть ct_phone. HTTP сервис сам запросы и query не журналирует.

ct_phone/ct_status/ct_dial_status не используются как доказательство. По ct_call_id
сначала ищется своя заявка на primary, затем call_by_id своим ключом. Подтверждение
только при pincode_ok и совпадении ID/телефона, через общий Confirm с локальным сроком.
HTTP 200 уходит после commit, повтор не создаёт секретов/сессий. Поздний verified
постбэк получает 200 без подтверждения. Чужой IP — 403, неизвестный call — 404,
неподтверждённый/несовпадающий статус — 400, недоступность API/БД — 503 для повтора.
Постбэк до сохранения provider_call_id может получить 404: повторы провайдера и
fallback уже открытого Watch покрывают этот промежуток.

Watch получает первый снимок из БД и сохраняет LISTEN/NOTIFY. Для pending после
таймера resync добавляется редкая проверка статуса: не чаще ZVONOK_POLL_INTERVAL
(30 секунд) на заявку в процессе. Карта ожиданий ограничена PHONE_WATCH_MAX_STREAMS;
переполнение наблюдается, общий API gate ограничивает все реплики. Ошибки провайдера
не рвут здоровый поток: остаются NOTIFY и локальный срок. При истечении срока есть
финальная проверка, но она не разрешает подтвердить локально истёкшую заявку.
Дедлайн Watch по-прежнему expires_at + 10 секунд. Удаление аккаунта не позволяет
provider proof восстановить удалённую строку или создать сессию заново.

## Метрики и отложенный контроль баланса

Метрики и примеры алертов перечислены в [server.md](server.md). Публичные номера пула
допустимы в метках отдельно от личных телефонов: не более 256 значений на процесс,
затем other и overflow. Задание раз в минуту читает rolling-итоги созданных за 24 ч
заявок: pending / confirmed / expired. Это gauges, не монотонные счётчики: удаление
аккаунта и retention уменьшают их. Реплики видят одну БД — **не суммировать реплики**.
В логах — агрегаты по публичному номеру/исходу, без телефона клиента и ID заявки;
не более 1024 детальных групп за итерацию. При overflow точные общие итоги остаются
в other, часть номеров видна только в логах/следующих снимках. Это диагностика пула,
а не журнал каждой заявки с гарантией exactly-once.

По решению владельца 24.10.2026 собственный контроль баланса отложен в
[FIN-233](https://finassist.youtrack.cloud/issue/FIN-233). Сейчас достаточно уведомлений
Zvonok о низком остатке. Сервис не опрашивает `users/balance`, не разбирает balance
из confirm и не публикует метрики/алерты остатка или свежести баланса. Запрошенный
у поддержки пример ответа понадобится для отдельной задачи и не блокирует FIN-139/216.
При нехватке предоплаты платные функции останавливает сам Zvonok; его явный отказ
проходит общий путь возврата. Защита общего бюджета FIN-81 остаётся отдельно.
Перед активацией нужна проверка реальной кампании и ingress владельцем.
Тесты используют HTTPS-сервер без платных API-запросов и реальный PostgreSQL 18.
