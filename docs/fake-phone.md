# Фейк обратного звонка (FIN-122)

`PHONE_PROVIDER=fake` включает бесплатный вход без звонка в `ENV=dev` или
`stage`. По умолчанию провайдер `disabled`. Фейк не открывает HTTP-постбэк,
не создаёт HTTP-клиент Zvonok и не принимает его ключ или кампанию.

Принимается только `+7000000xxxx`, где `xxxx` — четыре цифры. Например,
`+70000001234`. Это внутренние синтетические идентификаторы, **не официально
выделенный тестовый диапазон**. Их нельзя отправлять реальному провайдеру или
использовать как реальные телефоны. В режиме fake любой другой номер получает
обычный отказ создания (`INTERNAL`); реального fallback нет, резерв четырёх
лимитов возвращается по общему протоколу явного отказа.

Пул содержит `+70000000001` и `+70000000002` — синтетические значения для
отображения, звонить на них не нужно. Общий selector выбирает один равномерно и
сохраняет оба номера и выбор. Контракт для клиента тот же, что у Zvonok.

## Локальный запуск

С PostgreSQL в compose:

```sh
PHONE_PROVIDER=fake make up
```

Для бинарника на хосте (PostgreSQL и миграции уже подготовлены по README):

```sh
PHONE_PROVIDER=fake make run
```

На стенде: `ENV=stage PHONE_PROVIDER=fake`, штатные сервисные JWT, ключ подписи
пользователя, отдельные AES-ключи replay/результатов и обычные ограничения сети.
Фейк меняет только подтверждение телефона; он не выключает аутентификацию.

Вызвать StartPhoneVerification с тестовым телефоном, новым ключом идемпотентности, отдельными true age_confirmed/pd_consent_accepted и актуальным pd_consent_version,
затем открыть WatchPhoneVerification с полученным секретом. Первое состояние уже
VERIFIED: новому пользователю выдаётся регистрационный токен, существующему —
обычная сессия. Регистрация требует опубликованных документов согласий; тестовые
документы автотестов не публикуются в стенд автоматически.

## Транзакции и повторы

Создание проходит через общий Starter, включая телефонные/IP-лимиты и durable
claim. Фейк восстанавливает call_id, дату и пул из этой попытки без памяти процесса.
Срок заявки — 5 минут от исходного создания, recovery его не продлевает.

В транзакции завершения Starter сохраняет заявку, пул и выбранный номер, вызывает
общий Confirm и сохраняет зашифрованный идемпотентный ответ. Confirm использует тот
же код выдачи сессий/регистрационного токена, шифрования и pg_notify. Вложенный
db.Run присоединяется к внешней транзакции, поэтому ошибка любого шага откатывает
все эти эффекты; незавершённая попытка остаётся для повтора своим ключом.
Промежутка между коммитом создания и автоподтверждением нет.
Внутренний ConfirmCreated использует общую реализацию Confirm с владельцем,
которого Start определил и заблокировал до блокировки заявки. Повторного поиска
аккаунта под блокировкой заявки нет; порядок Guard → user → request сохраняется.

Повтор успешного Start не создаёт сессию и не выбирает номер заново.
Результат живёт 15 минут от подтверждения; Watch читает обычное состояние.
LISTEN/NOTIFY и subscribe-then-reread остаются общими, хотя первый снимок фейка
обычно уже подтверждён. Очистка, удаление аккаунта, Register, Refresh и их лимиты
работают без исключений для fake.

## Prod и наблюдаемость

С `ENV=prod PHONE_PROVIDER=fake` сервис не стартует, в том числе при прямой
сборке App без загрузчика env. Дополнительно общий Confirm в prod отклоняет
служебный диапазон независимо от провайдера, увеличивает
`finassist_phone_test_confirmation_rejected_total` и пишет ERROR без телефона,
call_id или секретов. Метрика считает попытки, включая отклонённые и откатившиеся;
меток у неё нет. В dev/stage она не регистрируется.

Готовое правило — [deploy/prometheus/phone.rules.yml](../deploy/prometheus/phone.rules.yml).
При развёртывании мониторинга загрузить его в vmalert/Prometheus и настроить
маршрутизацию critical в Alertmanager. Сейчас конфигурации мониторинга в infra нет,
правило этим PR не активируется. Выражение `counter > 0` ловит и первый scrape
после инцидента; сигнал держится до перезапуска процесса. До перезапуска сначала
разобрать ERROR и конфигурацию окружения.

Общие метрики лимитов, Watch и исходов по двум синтетическим callback_number
работают как у Zvonok; новые приватные метки не добавляются.
Защита общего бюджета FIN-81 остаётся отдельной задачей и условием включения
реального Zvonok в prod.

FIN-364 применяет к fake те же consent/14+/receipt/dispatch/terminal-key gates, что
к внешнему адаптеру. Stateless Recover восстанавливает только свою identity и
first_dispatch_at, не меняет исходный provider TTL; ε=0 без внешних часов. Доказательство
сохраняется до Create, линковка с аккаунтом — только после общего Confirm/Register.
