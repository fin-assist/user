# Лимиты аутентификации

FIN-219: общий механизм для StartPhoneVerification, WatchPhoneVerification, Register
и RefreshTokens. В этом этапе RPC аутентификации ещё не реализованы: публикация
настроек сама по себе не означает, что вход работает и ограничения уже применяются
к клиентским вызовам. Интеграционные API-тесты каждого RPC придут вместе с ним.

| scope в метриках | Значение по умолчанию | Субъект |
| --- | --- | --- |
| verification_phone_short | 3 / 1 час | телефон |
| verification_phone_long | 10 / 24 часа | телефон |
| verification_ip_short | 30 / 1 минута | доверенный x-client-ip |
| verification_ip_long | 300 / 1 час | доверенный x-client-ip |
| watch_ip | 60 подключений / 1 минута | доверенный x-client-ip |
| register_ip | 30 запросов / 1 минута | доверенный x-client-ip |
| refresh_ip | 120 запросов / 1 минута | доверенный x-client-ip |

Пределы — положительные числа до 2147483647; окна — целое число секунд от 1 секунды
до 24 часов. Переменные и их значения генерируются из Vars в [config.md](config.md).
Границы фиксированы в UTC, не зависят от часового пояса устройства или профиля;
точное равенство концу окна относится к следующему окну. Фиксированные окна допускают
два полных лимита по разные стороны границы — это свойство выбранной модели FIN-112.
Watch ограничивает попытки открыть поток, включая неверный токен, а не события и не
число одновременно открытых потоков. Глобальная защита бюджета остаётся FIN-81.

## Транзакции и порядок проверок

Limiter.Check вызывается в primary-транзакции сервиса. Репозиторий сначала блокирует
строки всех окон в стабильном порядке scope, затем сравнивает hits с пределами. Если
хотя бы одно окно исчерпано, ни один hits не увеличивается; RetryAt — самый поздний
конец исчерпанного окна. При разрешении все счётчики увеличиваются в той же транзакции.
Две реплики сервиса используют общие строки и не могут независимо потратить один остаток.
Пустой, некорректный или содержащий zone IP отклоняется; IPv4-mapped IPv6 приводится
к IPv4, чтобы два представления одного адреса не обходили лимит.

Интеграция сценариев обязана соблюдать порядок контракта:

- Идемпотентность исключает воспроизведение и конфликт до Check. Повтор сохранённого
  ответа не вызывает Check и не расходует лимит. Сквозные тесты этого порядка есть
  в AuthService с go-idempotency; сам Limiter ключи идемпотентности не принимает.
- Start проверяет четыре окна до занятости номера и обращения к провайдеру. Списание
  успешно выполненной попытки и сохраняемого отказа по дублю должно коммититься вместе
  с результатом. Неопределённый исход провайдера и восстановление — отдельная часть
  сценария Start; ответы Zvonok учтены в FIN-139/FIN-219, здесь эта политика не определяется.
- Watch, Register и Refresh проверяют IP до секрета из запроса. Отклонённая по токену
  попытка тоже учитывается: её лимит коммитится до возврата ошибки токена. Нельзя
  откатывать этот счётчик вместе с INVALID_TOKEN, иначе подбор не будет ограничен.
- Решение о превышении — Decision, не ошибка транзакции. После завершения транзакции
  сценарий возвращает finerr.RateLimited(RetryAt). Ошибка репозитория требует отката.

Check возвращает Receipt без телефона/IP. Только после успешного db.Run вызывается
receipt.Committed(); после отката receipt отбрасывается. Повторный вызов Committed
безвреден, в том числе для копии receipt. Это сохраняет различие между проверкой
и реально списанной попыткой; Committed не делает запросов к БД.

Ключ scope в БД имеет вид `watch_ip:60`: фиксированное имя политики и настроенное число
секунд. При смене длительности новые окна не переиспользуют строки со старым window_end.
Изменение политики начинает действовать после рестарта; для строгого единого предела
реплики обновляются согласованно. Смена окна создаёт новую серию счётчиков и может дать
новый остаток — это операционное изменение политики, не обычная ротация подов.

Очистка запускается каждую минуту в каждом экземпляре: до 1000 строк за проход,
window_end не позднее текущего времени минус 1 час, таймаут 5 секунд. Заблокированные
строки пропускаются через SKIP LOCKED; действующие окна не удаляются. Субъекты содержат
ПДн и удаляются с окнами, а не по user_id (решение FIN-112).

## Метрики и алерты

Все пять семейств доступны через штатный /metrics; в метках только семь scope и
результат из allowed/denied/error. Телефонов, IP, user_id, ключей и токенов нет.

| Метрика | Смысл |
| --- | --- |
| finassist_rate_limit_configured_limit{scope} | настроенный предел; доступен до первых запросов |
| finassist_rate_limit_window_seconds{scope} | настроенная длина окна; доступна до первых запросов |
| finassist_rate_limit_checks_total{scope,result} | завершённые проверки, включая последующий откат; denied — именно исчерпанное окно, error — ошибка проверки |
| finassist_rate_limit_consumed_total{scope} | только списания после коммита; без откатов и повторного Committed |
| finassist_rate_limit_window_utilization_ratio{scope} | histogram доли hits/limit после коммита разрешённой попытки или отказа; один образец на проверенное окно |

Histogram — распределение наблюдений по проверяемым субъектам, взвешенное их
активностью, не снимок всех живых окон. P95 может скрыть редкий перегруженный адрес:
следует смотреть также отказы. Счётчики checks и consumed имеют разный смысл;
разность не равна числу ошибок и не служит самостоятельным алертом.

Примеры выражений для правил мониторинга (порог, период, выдержка и минимальный трафик
должны быть параметрами конфигурации infra, а не константами сервиса):

```promql
# Приближение к пределу: пример P95 > 0.75 за 10 минут.
histogram_quantile(0.95,
  sum by (le, scope) (rate(finassist_rate_limit_window_utilization_ratio_bucket[10m]))
) > 0.75

# Рост доли отказов: пример > 10% за 10 минут при как минимум 20 проверках.
(
  sum by (scope) (increase(finassist_rate_limit_checks_total{result="denied"}[10m]))
  / clamp_min(sum by (scope) (increase(finassist_rate_limit_checks_total{result=~"allowed|denied"}[10m])), 1)
  > 0.10
)
and on (scope)
  sum by (scope) (increase(finassist_rate_limit_checks_total{result=~"allowed|denied"}[10m])) >= 20

# Ошибки проверки: сигнал о проблеме хранилища, отдельно от штатного ограничения.
sum by (scope) (increase(finassist_rate_limit_checks_total{result="error"}[5m])) > 0

# Расхождение настроек между репликами одного окружения.
max by (scope) (finassist_rate_limit_configured_limit)
  != min by (scope) (finassist_rate_limit_configured_limit)
```

Для приближения к порогу нужен фильтр минимального числа histogram-наблюдений, например
increase(finassist_rate_limit_window_utilization_ratio_count[10m]) >= 20 после агрегации
по scope. Для коротких политик с небольшим пределом порог подбирается отдельно: при
3 попытках/час заполнение имеет только значения 1/3, 2/3 и 1. Порог 0.6 предупредит
на второй попытке. Для всех примеров ограничьте выборку одним окружением/job, чтобы
не сравнивать dev и prod. Для window_seconds проверка расхождения такая же, как для
configured_limit. Пример выдержки (`for`) — 5 минут; подбирается по фактическому трафику.

Это описание выражений, не развёрнутые правила. Перенос в infra, проверка Prometheus
и включение уведомлений учитываются отдельно. FIN-81 также требует своих глобальных
лимитов, метрик конверсии и бюджетных алертов.
