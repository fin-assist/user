# Регистрация и refresh-сессии

Этап FIN-219: Register, RefreshTokens и Logout по api.md 1.3–1.5, grpc-api.md 6/7.1.
Вызывающий — bank-bff. Register и RefreshTokens — без пользовательского токена
(ModelNoUser); Logout — с access-токеном (ModelUser, отдельное точное правило
AccessPolicy по grpc-api.md 3.3, FIN-285). Создание заявки,
общее подтверждение и Watch — [verification.md](verification.md). Сквозные API-тесты
проходят Start с управляемым адаптером; публичного хука обхода звонка нет.
Runtime-провайдеры — FIN-122/139, выбор/хранение пула — FIN-216.

## Порядок и транзакции

Обработчик вызывает штатный UnaryInterceptor go-idempotency после общей проверки
сервисной идентичности/доступа. Он извлекает ровно один UUID idempotency-key с пустым
scope; хеш тела — HashProto. Сохраняются protobuf-ответы и разрешённые библиотекой
ошибки (400/422); 401/403/429 требуют rollback ключа и эффекта.

Порядок: ключ/replay/конфликт → IP-лимит → токен → бизнес-проверки → эффект + ключ.
Чтобы отказ по токену всё равно расходовал лимит, попытка коммитится отдельной
короткой транзакцией обычного pool. Транзакция ключа/эффекта использует отдельный
primary pool AUTH_DB_MAX_CONNS: она не занимает соединения, нужные счётчику.
Replay и конфликт до счётчика не доходят. Отказ по лимиту попытку не списывает
и не сохраняется. Сбой после уже сохранённой попытки не отменяет факт запроса.
Receipt.Committed обновляет метрики только после commit счётчика.

WithCompletion ограничивает эффект и commit 30 секундами: до callback отмена
учитывается библиотекой, после его начала эффект доводится независимо от клиента.

## Регистрация

registration_token ищется по SHA-256 на primary. Нужны подтверждённая заявка нового
пользователя, не закрытый результат и время строго меньше verified_at + 15 минут.
После срока — TOKEN_EXPIRED, неизвестный/израсходованный — INVALID_TOKEN. Отказ
CONSENT_REQUIRED/CONSENT_OUTDATED или неверный IANA timezone токен не расходует.

Документ и возраст проверяются в Start до передачи номера. Register повторно получает
обязательные PD assertions: true и исходную версию из receipt (1–64 Unicode символа).
Текущая версия повторно не запрашивается: смена документа во время звонка не отменяет
принятую заявку/15-минутный результат. Assertion не подменяет доказательство.
user_consent.granted_at берётся из исходного receipt, как и факт14+, а не из Register.
Без evidence старый registration_token не принимается. Связь receipt с подтверждённым
аккаунтом коммитится вместе с созданием/сессией/расходованием токена.

Новый аккаунт получает UUIDv7 PostgreSQL 18, тему system, timezone запроса или
Europe/Moscow, settings_version=1, согласие на ПДн, первую refresh-сессию и начальное
событие timezone. Всё вместе с закрытием заявки, стиранием result_ciphertext/result_key_id,
привязкой владельца replay и сохранением ответа — одна транзакция.

Решение владельца 23.10.2026: две разные подтверждённые заявки нового номера могут
дойти до Register, когда первая уже создала аккаунт. Вторая создаёт отдельную сессию
этого аккаунта, сохраняя его настройки и историю согласий; initial outbox не повторяется.
Одноразовость каждого registration_token сохраняется. Блокировки: guard пользователя
→ app_user → phone_verification. Предварительная вставка при последующем отказе
откатывается; уникальный phone сериализует создание одного аккаунта.

## Refresh, reuse и Logout

Refresh находит неистёкшее звено, берёт tombstone guard, блокирует auth_session, затем
refresh_token. Живой refresh меняется на новую пару; старое звено хранится до своего
expires_at. generation растёт на 1; переполнение отклоняется без записи. rotated_at
не уходит назад относительно issued_at при коррекции часов. Скользящий срок
REFRESH_TOKEN_TTL — по умолчанию 1440h (60 дней).

Первый refresh закрывает связанную заявку и стирает её результат для повторной
доставки. Уже закрытая заявка допускает дальнейшие ротации только своего пользователя.
Отозванная цепочка — TOKEN_REVOKED; неизвестный/истёкший refresh — INVALID_TOKEN.

Тот же ключ в течение 60 секунд возвращает ту же зашифрованную пару. Новый ключ или
истёкший replay TTL приводит к обнаружению rotated_at. Библиотека откатывает
несохраняемую 401, поэтому отзыв завершается после rollback в новой транзакции:
секрет/пользователь/звено проверяются заново, цепочка отзывается, и только после commit
возвращается TOKEN_REVOKED. Ошибка завершения даёт INTERNAL; повтор безопасен.
Ротации, успевшие между транзакциями, тоже входят в отозванную цепочку.

Logout требует проверенный access JWT: владелец берётся из sub, не из refresh.
Удаляется цепочка и все звенья по хешу любого её refresh, только если цепочка
принадлежит этому пользователю (`AND user_id=$2`). Неизвестный, повторный и чужой
refresh — OK без эффекта: ответ не подтверждает существование чужой сессии. Без
access-токена — INVALID_TOKEN, удалённый пользователь — TOKEN_REVOKED (tombstone в
интерцепторе). Access JWT остаётся действительным до своего срока (15 минут).

## Секреты, удаление и очистка

AUTH_IDEMPOTENCY_KEY_FILE обязателен: ровно 32 raw-байта AES-256 в обычном файле только
для владельца (0600; credential systemd в `$CREDENTIALS_DIRECTORY` — 0400 или 0440, [config.md](config.md)). Один ключ используется всеми репликами; он отдельный от
PHONE_RESULT_KEY_FILE результата phone_verification и от Ed25519. Ответ Register хранится 24 часа,
Refresh — 60 секунд. Ключ нужно сохранять до истечения всех зашифрованных записей.
API go-idempotency v0.6.0 использует один ключ: ранняя замена делает старый ответ
нечитаемым, не разрешая повторный эффект. Плановая замена — после истечения записей.
make dev-key создаёт локальный AES-ключ без перезаписи; helper и .local в образ не входят.

go-idempotency v0.6.0 (владение из FIN-226) хранит OwnerID в той же записи idempotency_keys, что и
зашифрованный ответ; callback задаёт реальный user_id после проверки секрета.
Успешный replay требует непустой OwnerID и проверяет его tombstone в той же
транзакции. Общий scope сохраняется. DeleteAccount адресно удаляет строки
`WHERE scope=$1::uuid OR owner_id=$1::uuid` вместе с данными пользователя; nil-scope
целиком не очищается. Отдельной таблицы связей нет. При конкурирующем replay удаление освобождает Guard
и повторяет транзакцию вместо ожидания ключа под Guard — [deletion.md](deletion.md).

auth-cleanup раз в минуту удаляет пачками по 1000 с общим дедлайном 5 секунд:
истёкшие ключи библиотеки вместе с владельцем, истёкшие refresh-звенья, пустые
сессии. Полные пачки продолжаются до малого остатка/дедлайна. SKIP LOCKED пропускает
занятые строки; живой successor и ещё неистёкшие звенья сохраняются. Очистка заявок
и их 15-минутного результата подключена отдельным phone-cleanup — [verification.md](verification.md).

finassist_idempotency_requests_total{endpoint,outcome} содержит только два настроенных
endpoint и исходы new/replay/conflict/in_progress: решения до внешнего commit,
не число сохранённых эффектов. Лимиты и алерты — limits.md; секреты метками не становятся.

## Проверки

Юнит-тесты: сроки, одноразовость, поколения, ошибки зависимостей, маппинг, учёт попыток.
PostgreSQL: реальные запросы/блокировки, FK, primary при пустой replica, очистка и живое
звено. API: подпись JWT, регистрация/initial timezone, replay/конфликт, ошибки и лимиты,
конкурентные Register/Refresh, reuse, Logout, отмена после эффекта, откат при ошибке
сохранения ответа, SQL-ошибки без утечки и tombstone перед выдачей cached-секрета.
